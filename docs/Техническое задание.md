### 3. Функциональные требования

#### 3.1. Сбор рыночных данных
- Система должна получать рыночные данные по настраиваемому списку финансовых инструментов через **gRPC-стримы** `MarketDataStreamService` (bi-directional stream) Tinkoff Invest API — не polling
- Состав подписок по каждому инструменту:
  - **Candles** — свечи (OHLCV), интервал 1 мин, `waiting_close=false` (обновление каждую секунду)
  - **OrderBook** — стакан заявок, depth=10 (для анализа микроструктуры и order imbalance)
  - **Trades** — лента обезличенных сделок (для оценки потока ордеров)
  - **Info** — торговые статусы (торговать только при `NORMAL_TRADING`)
- При старте Collector подписывается на все инструменты из конфигурации в одном стрим-соединении (лимит — 300 подписок на соединение, зависит от грейда API)
- При потере соединения — автоматическое переподключение с exponential backoff и повторной подпиской
- Данные должны публиковаться в Kafka-топик `raw-market-data` для дальнейшей обработки
- Метаданные инструментов (lot, min_price_increment, trading_status, api_trade_available_flag) кэшируются локально и периодически обновляются через `InstrumentsService`

#### 3.2. Анализ рынка
- Система должна рассчитывать технические индикаторы (RSI, MACD, Bollinger Bands и др.) на основе полученных данных
- На базе индикаторов должна формироваться оценка сигнала (BUY / SELL / HOLD)
- Результаты каждого анализа должны сохраняться в базу данных
- При обнаружении сигнала на покупку — событие должно быть отправлено в очередь для исполнения

#### 3.3. Исполнение сделок
- Система должна принимать сигналы из Kafka-топика `trading-signals` и исполнять ордера через Tinkoff Invest API
- **Идемпотентность**: каждый сигнал содержит `signal_id`; Trader дедуплицирует по `signal_id` (таблица `processed_signals` с TTL-окном). Идемпотентный ключ `order_id` передаётся в `PostOrderRequest`
- **Тип ордера на вход**: LIMIT (основной) или BESTPRICE (опционально). **Рыночные ордера (MARKET) запрещены на вход** из-за проскальзывания и максимальной комиссии
- **Защитные ордера (SL/TP)**: выставляются на стороне **биржи** через `StopOrdersService` (`PostStopOrder`) сразу после исполнения ордера на вход. Локальный мониторинг дублирует для alerting, но не является основным механизмом защиты
- **Проверка рисков перед исполнением** (конкретные пороги хранятся в `risk_config`, настраиваются без передеплоя):
  - **Убыток на сделку**: не более 1% депозита (2000 руб при депозите 200 000 руб). Размер позиции рассчитывается динамически из расстояния вход→SL
  - **Комиссионная рентабельность**: ожидаемая валовая прибыль должна минимум в 3-4 раза превышать суммарную комиссию за вход и выход. Сигналы, не проходящие порог, отбрасываются
  - **Максимум одновременных позиций**: 3
  - **Максимальное время удержания позиции**: 10 минут. По истечении — auto-close (сигнал на закрытие)
  - **Корреляционный лимит**: не открывать позиции по коррелированным инструментам (например, Si+BR при корреляции >0.8) — настраивается
  - **Лимит сделок в минуту**: self-rate-limit для защиты от зацикливания (настраивается)
  - **Проверка торгового статуса**: ордер выставляется только при `SECURITY_TRADING_STATUS_NORMAL_TRADING`
- **PnL Circuit Breaker** (торговый предохранитель, отдельный от API-Circuit Breaker):
  - При суммарном дневном убытке 3% депозита (6000 руб) — принудительно закрыть все открытые позиции и заблокировать выставление новых заявок до начала следующей торговой сессии
  - Порог настраивается в `risk_config` (диапазон 3-5%)
- Система должна мониторить открытые позиции через `PositionsStream` и закрывать их при срабатывании биржевых SL/TP
- Все сделки (успешные и неудачные) должны сохраняться в БД (`trade_results`) и публиковаться в Kafka `trade-results`
- **Recovery при старте**: Trader синхронизирует состояние — открытые позиции через `GetPositions`, in-flight ордера через `GetOrders`, биржевые стоп-ордера через `GetStopOrders`

### 4. Архитектура системы

#### 4.1. Компоненты

| Компонент | Язык | Назначение |
|-----------|------|------------|
| Data Collector | Java 21 + Spring Boot | Сбор данных с биржи, публикация в Kafka |
| Analyzer | Python 3.11+ + pandas/talib | Анализ данных, генерация сигналов |
| Trader | Java 21 + Spring Boot | Исполнение сделок, управление позициями |
| PostgreSQL 15 | SQL | Хранение результатов анализа и истории сделок |
| Apache Kafka | — | Асинхронный обмен сообщениями между модулями |

#### 4.2. Потоки данных

```
Tinkoff API
    │
    ▼
[Java Data Collector] ──publish──▶ Kafka: raw-market-data
                                          │
                                          ▼
                                  [Python Analyzer]
                                     │         │
                          save       │         │  signal (BUY/SELL)
                                     ▼         ▼
                              PostgreSQL    Kafka: trading-signals
                              (analysis)        │
                                                ▼
                                        [Java Trader]
                                           │         │
                                save       │         │  publish
                                           ▼         ▼
                                    PostgreSQL    Kafka: trade-results
                                    (trades)      (compact)
```

#### 4.3. Kafka-топики

| Топик | Назначение | Retention | Cleanup Policy |
|-------|------------|-----------|----------------|
| `raw-market-data` | Сырые рыночные данные | 3 мин | delete |
| `trading-signals` | Сигналы на покупку/продажу | 3 дня | delete |
| `trade-results` | События по сделкам | Бесконечно | compact |

### 5. Структура базы данных

> Миграции: Flyway (Java-модуль Trader — владелец). Python-модуль Analyzer пишет только в `analysis_results`.

#### 5.1. Таблица `instruments`
Справочник торговых инструментов. Кэшируется в памяти модулей, обновляется через `InstrumentsService`.

| Поле | Тип | Описание |
|------|-----|----------|
| `figi` | VARCHAR(32) PK | Financial Instrument Global Identifier |
| `uid` | UUID | Уникальный идентификатор T-Invest |
| `ticker` | VARCHAR(16) | Тикер (SBER, Si, BR, …) |
| `class_code` | VARCHAR(16) | Код секции (TQBR, SPBFUT, …) |
| `name` | VARCHAR(128) | Наименование |
| `instrument_type` | VARCHAR(16) | share / bond / future / currency / etf |
| `lot` | INT | Лотность |
| `min_price_increment` | DECIMAL | Минимальный шаг цены |
| `currency` | VARCHAR(8) | Валюта расчётов |
| `api_trade_available` | BOOLEAN | Доступность для API-торговли |
| `trading_status` | SMALLINT | Текущий торговый статус |
| `tier` | SMALLINT | Иерархия: 1=фьючерс, 2=голубая фишка, 3=валютный спот, 4=чёрный список |
| `updated_at` | TIMESTAMPTZ | Время последнего обновления |

#### 5.2. Таблица `analysis_results`
Результаты анализа по каждому инструменту. Пишется Python-модулем Analyzer.

| Поле | Тип | Описание |
|------|-----|----------|
| `signal_id` | UUID PK | Уникальный идентификатор сигнала (для идемпотентности) |
| `ts` | TIMESTAMPTZ | Время генерации сигнала |
| `instrument_id` | VARCHAR(32) FK→instruments.figi | Инструмент |
| `candle_ts` | TIMESTAMPTZ | Время свечи, по которой сгенерирован сигнал |
| `candle_interval` | VARCHAR(8) | Интервал свечи (1min, 5min, …) |
| `strategy_id` | VARCHAR(32) | Идентификатор стратегии |
| `analyzer_version` | VARCHAR(16) | Версия Analyzer (для воспроизводимости) |
| `indicators` | JSONB | Значения индикаторов: {rsi, macd, macd_signal, bb_upper, bb_middle, bb_lower, atr, vwap, order_imbalance} |
| `signal` | VARCHAR(8) | BUY / SELL / HOLD |
| `confidence` | DECIMAL(5,4) | Уверенность сигнала 0.0–1.0 |
| `suggested_price` | DECIMAL | Предлагаемая цена входа (лимитная) |
| `suggested_sl` | DECIMAL | Предлагаемый Stop-Loss (от ATR) |
| `suggested_tp` | DECIMAL | Предлагаемый Take-Profit |
| `position_size_hint` | INT | Рекомендуемый размер позиции в лотах |
| `expires_at` | TIMESTAMPTZ | Время устаревания сигнала (сигнал живёт секунды) |

Индексы: `(instrument_id, ts DESC)`, `(signal, ts DESC)`, `(expires_at)`.

История всех торговых операций. Связана с породившим сигналом.

| Поле | Тип | Описание |
|------|-----|----------|
| `trade_id` | UUID PK | Внутренний идентификатор сделки |

| `instrument_id` | VARCHAR(32) FK→instruments.figi | Инструмент |
| `direction` | VARCHAR(4) | BUY / SELL |
| `quantity_lots` | INT | Количество лотов |
| `order_id` | VARCHAR(36) | Идемпотентный ключ, переданный в `PostOrderRequest` |
| `exchange_order_id` | VARCHAR(64) | Биржевой идентификатор ордера |
| `price_entry` | DECIMAL | Цена входа |
| `price_exit` | DECIMAL | Цена выхода (NULL пока открыта) |
| `commission` | DECIMAL | Суммарная комиссия |
| `pnl` | DECIMAL | Финансовый результат (NULL пока открыта) |

Индексы: `(instrument_id, opened_at DESC)`, `(status)`, `(signal_id)`.

#### 5.4. Таблица `positions`

| Поле | Тип | Описание |
|------|-----|----------|

| `unrealized_pnl` | DECIMAL | Нереализованный P&L |
| `opened_at` | TIMESTAMPTZ | Время открытия позиции |
| `trade_id` | UUID FK→trade_results.trade_id | Связь с сделкой открытия |
| `updated_at` | TIMESTAMPTZ | Время последнего обновления |

#### 5.5. Таблица `orders`
История заявок (включая отменённые и отклонённые).

|------|-----|----------|

| Поле | Тип | Описание |
|------|-----|----------|
| `key` | VARCHAR(64) PK | Параметр (max_loss_per_trade_pct, pnl_circuit_breaker_pct, …) |

### 6. Форматы сообщений

> Сериализация: **Protobuf** (едина с T-Invest API). `.proto`-файлы хранятся в репозитории, генерация кода — при сборке. Внешний schema registry для MVP не используется.

#### 6.1. `raw-market-data`
Сырые рыночные данные от Collector. Один топик, несколько типов сообщений (различаются по `payload_type`).

```protobuf
message RawMarketData {
  string figi = 1;                          // идентификатор инструмента
  google.protobuf.Timestamp ts = 2;         // время события
  PayloadType payload_type = 3;             // тип данных
  oneof payload {
    Candle candle = 10;
    OrderBook order_book = 11;
    Trade trade = 12;
    TradingStatusInfo info = 13;
  }
}

enum PayloadType { CANDLE = 0; ORDER_BOOK = 1; TRADE = 2; INFO = 3; }

message Candle {
  google.protobuf.Timestamp begin = 1;
  google.protobuf.Timestamp end = 2;
  Quotation open = 3;
  Quotation close = 4;
  Quotation high = 5;
  Quotation low = 6;
  int64 volume = 7;                         // в лотах
  bool is_complete = 8;
}

message OrderBook {
  repeated OrderBookItem bids = 1;          // до 10 уровней
  repeated OrderBookItem asks = 2;
  Quotation limit_price_up = 3;             // верхний предел цены
  Quotation limit_price_down = 4;
}

message OrderBookItem {
  Quotation price = 1;
  int64 quantity = 2;                       // в лотах
}

message Trade {
  Quotation price = 1;
  int64 quantity = 2;                       // в лотах
  string trade_id = 3;
  TradeDirection direction = 4;             // buy / sell / unspecified
}

message TradingStatusInfo {
  int32 trading_status = 1;                 // SecurityTradingStatus
  int32 limit_order_available_flag = 2;
  int32 market_order_available_flag = 3;
}
```

#### 6.2. `trading-signals`
Сигналы от Analyzer к Trader. Каждый сигнал имеет `signal_id` для идемпотентности и `expires_at` — устаревший сигнал Trader отбрасывает.

```protobuf
message TradingSignal {
  string signal_id = 1;                     // UUID, идемпотентность
  string figi = 2;
  google.protobuf.Timestamp ts = 3;         // время генерации
  google.protobuf.Timestamp expires_at = 4; // время устаревания
  SignalType signal = 5;                    // BUY / SELL / HOLD
  float confidence = 6;                     // 0.0–1.0
  string strategy_id = 7;
  string analyzer_version = 8;
  Quotation suggested_price = 9;            // предлагаемая цена входа
  Quotation suggested_sl = 10;              // предлагаемый Stop-Loss
  Quotation suggested_tp = 11;              // предлагаемый Take-Profit
  int32 position_size_hint = 12;            // рекомендуемый размер в лотах
  map<string, float> indicators = 13;       // значения индикаторов (для аудита)
}

enum SignalType { BUY = 0; SELL = 1; HOLD = 2; }
```

#### 6.3. `trade-results`
События по сделкам от Trader. Топик `compact` — ключ `trade_id`, значение — актуальное состояние сделки.

```protobuf
message TradeResult {
  string trade_id = 1;                      // UUID сделки
  string signal_id = 2;                     // сигнал-источник (может быть пустым)
  string figi = 3;
  TradeEventType event_type = 4;            // тип события
  google.protobuf.Timestamp ts = 5;
  string order_id = 6;                      // идемпотентный ключ
  string exchange_order_id = 7;
  TradeDirection direction = 8;
  int32 quantity_lots = 9;
  Quotation price = 10;                     // цена исполнения
  Quotation commission = 11;
  Quotation pnl = 12;                       // для событий закрытия
  string reject_reason = 13;                // для reject
}

enum TradeEventType {
  OPENED = 0;          // позиция открыта (ордер исполнен)
  PARTIAL_FILL = 1;    // частичное исполнение
  SL_HIT = 2;          // сработал Stop-Loss
  TP_HIT = 3;          // сработал Take-Profit
  TIMEOUT_CLOSED = 4;  // закрытие по таймауту удержания
  REJECTED = 5;        // ордер отклонён
  CANCELLED = 6;       // ордер отменён
  CLOSED = 7;          // позиция полностью закрыта
}
```

### 7. Нефункциональные требования

#### 7.1. Производительность
- Задержка pipeline (Collector → Analyzer → Trader) не более 2 секунд. Бюджет по компонентам:
  - gRPC-stream приём данных: ≤ 50 мс
  - Kafka produce `raw-market-data`: ≤ 20 мс
  - Python Analyzer (consume + индикаторы + сигнал): ≤ 500 мс на инструмент (ta-lib, без ML в MVP)
  - Kafka produce `trading-signals`: ≤ 20 мс
  - Java Trader (consume + risk-check + `PostOrder` gRPC): ≤ 200 мс
  - Reserve: ~1210 мс
- **MVP**: 3 торгуемых инструмента (BR, SBER, TCSG) + watchlist без торговли. 100 инструментов — потолок масштабирования (зависит от грейда API: грейд 2+ даёт 4 stream-соединения = до 100 инструментов с полным набором подписок)
- Время исполнения ордера после получения сигнала (от consume `trading-signals` до `EXECUTION_REPORT_STATUS_NEW`): не более 500 мс

#### 7.2. Надежность
- Все компоненты должны иметь механизмы retry при сбоях
- Использование Dead Letter Queue для обработки ошибочных сообщений
- Circuit Breaker для взаимодействия с внешним API
- Идемпотентность обработки сигналов

#### 7.3. Масштабируемость
- Возможность горизонтального масштабирования Analyzer через добавление consumer-инстансов
- Независимое масштабирование Collector и Trader

#### 7.4. Мониторинг
- Метрики Prometheus по Java-модулям (Collector, Trader)
- Метрики Prometheus по Python-модулю Analyzer (`prometheus_client`)
- **Бизнес-метрики**: PnL (realized/unrealized), drawdown, win rate, SL/TP hit count, latency per stage (collector→analyzer→trader), consumer lag, signals/min, trades/min, rejects/min
- **Alerting** (критические алерты):
  - API disconnect (потеря gRPC-стрима)
  - Token error (`40003` — токен невалиден)
  - PnL Circuit Breaker сработал
  - Stale data (нет данных по инструменту > 30 сек)
  - Consumer lag > 1000 сообщений
  - Ордер rejected (с причиной)
  - Токен истекает через 7 дней

### 9. Ограничения и допущения

- Используется только API Т-Инвестиций (sandbox или prod)
- Торговля ведется только на Московской бирже
- Стратегия скальпинга предполагает удержание позиции от нескольких секунд до нескольких минут (максимум 10 минут — auto-close по таймауту)
- Токен API хранится в защищенном хранилище (environment variables / Vault)
- **Ротация токена**: токен живёт 3 месяца с даты последнего использования. Алерт за 7 дней до истечения. При ошибке `40003` — halt торговли + alert, ручной перевыпуск
- **Чёрный список инструментов** (торговля запрещена):
  - Акции 2-го и 3-го эшелона (низкая ликвидность, широкий спред, риск манипуляций)
  - Инструменты с дорогим лотом (стоимость одного лота > 30 000–40 000 руб)
  - Облигации (недостаточная внутридневная волатильность)
  - Валютный спот CNYRUB (замораживает ~65% депозита на одну позицию)
- **Лимит сделок**: сделки свыше 6 млн руб / $100 000 / €100 000 требуют подтверждения кодом и недоступны через API (неприменимо к депозиту 200 000 руб, но зафиксировано как ограничение)
- **Синхронизация времени**: все модули используют NTP — критично для скальпинга (синхронизация меток времени данных)
- **MVP-конфигурация**: 3 торгуемых инструмента (BR, SBER, TCSG). Отклонение от рекомендации «2+1» из recommendation.md принято владельцем депозита — 3 инструмента для диверсификации при max_positions=3
