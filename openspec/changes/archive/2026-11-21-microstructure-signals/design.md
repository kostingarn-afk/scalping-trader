# Design — microstructure-signals

## Context

См. `proposal.md` — Why. Факты из кода:

- `handler.parse_candle` (`handler.py:37-71`) возвращает только завершённые свечи, остальные
  payload'ы отбрасывает; `make_handler` (`:124`) строит `CandleWindow` и вызывает пайплайн.
- `main.process` (`main.py:55`) вызывает `compute_all(closes, highs, lows, volumes)` без
  `bids_qty/asks_qty`, хотя параметры у функции есть (`indicators.py:142-143`).
- `compute_order_imbalance` по умолчанию `depth=10`; стакан от Collector — до 10 уровней.
- Сообщение `Trade` несёт `direction` (buy/sell/unspecified) и объём в лотах.

## Goals / Non-Goals

**Goals:** стакан и сделки не теряются, OBI и VPIN попадают в `Indicators` и
`analysis_results`, модель микроструктуры использует оба.

**Non-Goals:** Avellaneda–Stoikov и котирование LIMIT (3.6), хранение истории стакана на диске,
пересчёт бэктеста с микроструктурой, изменение Collector/Trader.

## Decisions

### D1. Один разборщик, обёртка для совместимости

`parse_message(payload) -> (figi, kind, data) | None`, где `kind ∈ {candle, book, trade}`.
`parse_candle` делегирует и возвращает результат только для `candle`. Существующие вызовы и
тесты не меняются.

*Альтернатива:* отдельные `parse_book`/`parse_trade` с повторным `ParseFromString`. Отклонено:
три разбора одного сообщения.

### D2. Состояние микроструктуры — в handler, не в пайплайне

`MicrostructureState` живёт в процессе-консьюмере рядом с `CandleWindow`: состояние по figi,
обновляется на каждое сообщение, снимок приклеивается к данным свечи. Пайплайн остаётся
stateless по рыночным данным.

Почему не в `AnalyzerPipeline`: пайплайн вызывает asyncpg и publisher; добавление состояния
сделало бы его ответственным за порядок сообщений, который уже гарантирован внутри процесса
(partition by `instrument_id`).

### D3. VPIN — объёмные бакеты, только завершённые

`VolumeBuckets(bucket_volume, buckets)`: сделка с объёмом `v` распределяется по текущему бакету,
остаток переходит в следующий. `vpin = mean((buy − sell)/bucket_volume)` по последним `buckets`
завершённым. Меньше `buckets` — `None`.

*Альтернатива:* окно по времени. Отклонено: VPIN измеряет дисбаланс на единицу объёма, а не на
минуту; временное окно смешивает активность и дисбаланс.

### D4. Направление сделки: сообщение, иначе тик-правило

`direction` из protobuf (`buy/sell`) имеет приоритет. `UNSPECIFIED` → сравнение с предыдущей
ценой: выше — покупка, ниже — продажа, равна — предыдущее направление. Нет предыдущей цены →
сделка в бакеты не идёт (не угадываем).

### D5. Глубина стакана

`order_book_depth` (дефолт 10) ограничивает число уровней, попадающих в снимок. Collector уже
шлёт до 10; параметр нужен, если глубина уменьшится на стороне Collector.

### D6. Модель микроструктуры — stateless, только production-данные

`MicrostructureModel` не оценивает параметры (`fit` — no-op), читает `order_imbalance` и `vpin`
из `Indicators`. В бэктесте на CSV стакана нет, поэтому модель всегда HOLD: это ограничение
данных, а не баг. Тесты проверяют сигналы на синтетических индикаторах; edge проверяется в
production после накопления данных.

## Risks / Trade-offs

- **Частота сообщений стакана** → обновление O(depth) без numpy; VPIN O(1) на сделку.
- **`UNSPECIFIED` у части сделок** → выборка бакетов меньше; размер бакета конфигурируем.
- **Стакан устаревает** → снимок используется до следующего сообщения; для входа модель требует
  ещё и свечу, поэтому цена и стакан синхронны в пределах бара. Отдельный TTL не вводится: это
  следующий шаг (котирование 3.6).
- **Новые ключи в JSONB** → потребители читают JSON целиком; схема набор ключей не фиксирует.
- **Модель без бэктеста** → в отчётах 0 сделок; README и reason объясняют причину.

## Migration Plan

Аддитивно: новые модули, поля индикаторов и конфига. Откат — вернуть `parse_candle` без веток
book/trade и убрать модель из реестра. Миграций нет.

## Open Questions

- Нужен ли TTL стакана (считать устаревшим через N секунд) — влияет на вход по OBI в тихие
  периоды. Решается после наблюдения в production; на текущий шаг не влияет.
