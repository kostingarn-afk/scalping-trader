# Design — signal-model-protocol

## Context

См. `proposal.md` — Why. Текущее состояние, важное для решения:

- три правила — чистые функции с разными подписями: `mean_reversion(ind, price, atr_mult_sl,
  atr_mult_tp)` и две с конфигом-аргументом (`MomentumConfig`, `StrategyV2Config`);
- бэктест вызывает их через `StrategyFn = Callable[[Indicators, float, float, float], Signal]`
  (`backtest/engine.py:31`);
- список моделей для CLI задан трижды: `choices` (`cli.py:94`), `_strategy_config` (`:506`),
  `_builder_for` (`:552`), причём `_builder_for` не знает про третий тип конфига и уводит его в
  `momentum`;
- `Bar` объявлен в `backtest/models.py`; `backtest` импортирует production-модули, поэтому
  обратный импорт `signal_models → backtest.models` создал бы цикл.

## Goals / Non-Goals

**Goals:** единый контракт, реестр как единственный источник списка, нулевое изменение
поведения действующих правил, готовность к статистическим моделям (1.2–1.5) и гейту (1.8).

**Non-Goals:** перенос правил в production, обучение статистических моделей, изменение
`CommissionFilter`, изменение формата Protobuf, параметры `k×ATR`/тариф (шаги 1.9–1.10).

## Decisions

### D1. Структурный протокол, а не базовый класс

`typing.Protocol` с `runtime_checkable` для проверок в тестах. Существующие функции остаются
публичными и вызываемыми напрямую — адаптер лишь делегирует.

*Альтернатива:* ABC. Отклонено: заставило бы менять продовые функции, а множественное наследование
усложнило бы появление моделей с разной природой (правило vs оценка параметров).

### D2. `BarLike` вместо импорта `Bar`

`fit(history: Sequence[BarLike])`, где `BarLike` — протокол с `open/high/low/close/volume` и
необязательной меткой времени. `backtest.models.Bar` удовлетворяет ему структурно.

*Альтернатива:* перенести `Bar` в нейтральный модуль. Отклонено: шире диффа, ломает импорты
`loader`/`engine`/`report` без выгоды для 1.1.

### D3. `fit` обязателен, no-op разрешён контрактом

Правила без параметров реализуют `fit` как явный no-op с записью в docstring. Контракт требует
метод у всех: гейт и отчёт опрашивают модели единообразно, а «модель без fit» стала бы особым
случаем в каждом вызывающем месте.

### D4. Реестр — единственный источник имён

`MODEL_FACTORIES: Mapping[str, Callable[..., SignalModel]]` и `build_model(name, **params)`.
`build_model` на неизвестном имени бросает `KeyError` с перечнем доступных. CLI-аргумент
`--strategy` получает `choices=tuple(MODEL_FACTORIES)`, а `_strategy_config`/`_builder_for`
удаляются; их роль выполняет фабрика, принимающая `argparse.Namespace`-совместимый набор
параметров.

*Альтернатива:* оставить `_builder_for` и добавить ветку для каждого нового типа. Отклонено:
дефект `to_do.md:62` воспроизводится при каждой новой модели.

### D5. Параметры — неизменяемое отображение примитивов

`params()` возвращает `MappingProxyType` словаря примитивов (str/int/float/bool/None). Вложенные
структуры запрещены: отчёт и БД сериализуют их в JSON. Конфиг-классы остаются frozen dataclass —
`params()` лишь проецирует их поля.

### D6. Порядок совместимости

`backtest/engine.StrategyFn` не меняется: адаптер предоставляет `__call__(ind, price, sl, tp)`.
Так движок, `nullmodel`, `walkforward` и `panel` не затрагиваются, а протокол живёт над ними.

### D7. Проверка паритета — golden на фиксированном ряду

Тест строит детерминированный ряд (синус + ступеньки + фиксированный шум с seed), считает
`compute_all` один раз и для каждого бара сравнивает `model.predict(...)` с прямой функцией
(`==` по frozen dataclass). Дополнительно — сериализация `params()` в JSON и точный состав
реестра.

## Risks / Trade-offs

- **ta-lib дрейфует между версиями** → golden сравнивает адаптер и функцию в одном процессе, а не
  сохранённые числа; расхождение версий ta-lib не маскируется.
- **Реестр и CLI разойдутся** → `choices` вычисляется из реестра, тест сверяет состав и ошибку на
  неизвестном имени.
- **`params()` с несериализуемыми значениями** → контракт ограничен примитивами, тест проверяет
  `json.dumps`.
- **Двойной источник конфигов** (`AnalyzerConfig` vs конфиг модели) → в 1.1 не сливаются; связь
  `AnalyzerConfig.strategy_id` с именем модели проверяется в 1.9/1.10 при переключении.

## Migration Plan

Чисто аддитивно: новый пакет + правка CLI. Откат — удалить пакет и вернуть прежние три функции
выбора в CLI (они остаются в git-истории). Миграций БД и изменений форматов нет.

## Open Questions

Нет: решения, влияющие на спеки и разбиение задач, приняты. Вопрос «какая модель станет
production по умолчанию» относится к шагу 1.9/1.10, не к протоколу.
