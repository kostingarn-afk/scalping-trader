# Design

## D1. Переиспользование production-расчёта вместо отдельной реализации

**Решение.** Бэктест вызывает `analyzer.indicators.compute_all` и
`analyzer.strategy.mean_reversion` напрямую; собственных формул индикаторов в пакете нет.

**Почему.** Цель прогона — оценка той стратегии, которая работает в бою. Вторая реализация
индикаторов неизбежно разойдётся с первой (сглаживание, окна, порядок вычислений), и вопрос
«стратегия плоха или бэктест неверен» станет неразрешимым.

**Следствие.** Замер `to_be.md` §3 использовал упрощённые RSI/ATR; бэктест на talib даст другие
абсолютные значения при том же порядке величин. Это ожидаемо и фиксируется в отчёте.

**Альтернатива (отвергнута).** Отдельная быстрая реализация индикаторов на numpy ради скорости:
8 500 баров считаются talib за секунды, выигрыш не оправдывает риск расхождения.

## D2. Модель издержек живёт в бэктесте, production-фильтр не меняется

**Решение.** `backtest/commission.py` содержит тарифную сетку и расчёт комиссии за сторону и
за круг. `analyzer/commission_filter.py` (заглушка 0.3 %/сторона) остаётся как есть.

**Почему.** Правка `CommissionFilter` немедленно меняет поведение боевого контура: при тарифе
`trader` порог падает с 0.9 % до 0.15 %, и система начинает открывать сделки. Включать это
можно только после подтверждённого edge (`to_be.md` §4, Вариант 3 — «без варианта 1 это опасно»).

**Согласованность.** Тест `test_commission_filter_matches_production_away_from_threshold` фиксирует,
что при тарифе `investor` и `lot_size=1` решения совпадают везде, кроме узкой полосы у порога,
и `test_filter_deviation_from_production_is_confined_to_threshold_band` фиксирует саму полосу.
Источник расхождения — расчёт комиссии выхода: production берёт обе стороны по цене входа
(`0.006 × P`), бэктест — по фактическим ценам (`0.003 × (P + TP)`), то есть ≤1 % от порога.
Отказ от точного паритета выбран осознанно: модель по фактической цене выхода точнее, а
подгонка под заглушку 0.3 % закрепляла бы её ошибку.

## D3. CSV + sidecar `.meta.json` как контракт Collector → Analyzer

**Решение.** Collector пишет `{ticker}_{interval}min.csv` (`ts,open,high,low,close,volume`,
ISO-8601 UTC, `ts` — время **закрытия** свечи) и рядом `{ticker}_{interval}min.meta.json`
(`ticker`, `class_code`, `lot_size`, `interval_minutes`, `fetched_at`, `source`). Analyzer
читает каталог, использует meta для `Instrument`, при необходимости агрегирует 1 мин → 5/15 мин.

**Почему.** Модули не зависят друг от друга на уровне кода (AGENTS.md §3). CSV — единственный
формат, который читается глазами, диффится и не требует общих схем. Meta выносит справочные
данные (класс, лотность) из имени файла в явные поля и исключает ошибку «фьючерс посчитан
по тарифу бумаг».

**Конвенция времени.** `ts` — закрытие свечи (соответствует `end` у `Candle` в T-Invest и
полю `candle_ts` в `raw-market-data`). Агрегация группирует бары по времени открытия
(`ts − interval`), иначе 5-мин свеча собиралась бы из закрытий 07:00…07:04 и была бы смещена
на один нативный бар. Collector при выгрузке обязан писать именно закрытие — это условие
контракта, проверяемое при реализации волны 2.

**Валидация.** Загрузчик отвергает строки, нарушающие OHLC-инварианты, неположительные цены
и отрицательный объём, и проверяет, что шаг между свечами кратен `interval_minutes` — рассинхрон
meta и данных не должен молча попадать в агрегацию.

**Альтернативы (отвергнуты).** Parquet — требует новой зависимости; Protobuf — избыточен для
табличных OHLCV и требует генерации модулей ради выгрузки; чтение из БД — истории цен в БД нет.

## D4. Вход по открытию следующего бара

**Решение.** `RunConfig.fill_on_next_bar_open = True` по умолчанию: сигнал считается по закрытой
свече, вход — по `open` следующего бара. Флаг позволяет воспроизвести замер §3 (вход по закрытию
сигнального бара) для сверки.

**Почему.** В живом контуре сигнал уходит в Kafka после закрытия свечи, и LIMIT-заявка попадает
в стакан уже следующего бара. Вход по цене закрытия сигнального бара даёт несуществующую
возможность исполнения и завышает результат.

**Режим сверки.** При `fill_on_next_bar_open=False` бар входа не проверяется на выход: его
high/low сформировались до входа, и проверка дала бы lookahead (фиктивные TP/SL на том же баре).
Замер §3 таким правилом не страдал только потому, что считал выходы по последующим барам.

## D5. Внутрибарная неоднозначность решается в пользу SL

**Решение.** Если в одном баре цена коснулась и SL, и TP, фиксируется SL.

**Почему.** По бару неизвестно, какой уровень был достигнут первым. Пессимистичный выбор исключает
оптимизм, который в реальной торговле оплачивается деньгами. Замер §3 использовал то же правило.

**Ограничение.** Для тонких данных (1 мин на малоликвидных бумагах) консерватизм может быть
избыточным; при росте таймфрейма эффект уменьшается.

**Гэпы.** Если бар открывается за уровнем стопа, выход фиксируется по цене открытия, а не по
уровню: иначе ночной гэп записывался бы как выход по SL выше факта и сделка могла бы попасть
в прибыльные. Гэп в сторону TP консервативно считается по самому TP.

## D6. Риск-сайзинг с лимитом номинала

**Решение.** `lots = floor(risk_amount / (|entry − sl| × lot_size))`, затем
`lots = min(lots, floor(deposit × max_position_notional_pct / notional_per_lot))`; если получается
меньше одного лота — сделка пропускается и учитывается счётчиком `skipped_by_notional`.

**Почему.** На 1-мин баре ATR ≈ 0.028 %, стоп 1.5×ATR ≈ 0.042 % цены: риск 2 000 ₽ даёт
≈ 19 000 лотов (≈ 4.8 млн ₽ номинала на депозит 200 000 ₽). Такая сделка неисполнима и
искажает PnL. Лимит делает прогон сопоставимым с реальными ограничениями брокера.

**Следствие для плана.** Тот же параметр нужен в `RiskManager` (Вариант 5, шаг 4 плана) —
бэктест и боевой контур должны считать объём одинаково.

**Допущение по фьючерсам.** Номинал считается полной стоимостью контракта (котировка × лоты),
а не гарантийным обеспечением. Для фьючерсов это консервативнее реального ограничения брокера
(ГО составляет ~10–20 % стоимости): прогоны по `SiZ6` занижают допустимый объём в 5–10 раз.
Такой выбор сделан, чтобы сравнивать бумаги и фьючерсы в одной шкале риска; при необходимости
доля ГО добавляется отдельным параметром.

## D7. Один инструмент в позиции, новая сделка — после закрытия предыдущей

**Решение.** Движок держит не более одной позиции на инструмент; сканирование сигналов
возобновляется на баре после выхода.

**Почему.** Соответствует `max_positions` риск-контура: пирамидинг и хеджирование внутри одного
инструмента не предусмотрены. Модель «одна позиция» делает attribution PnL однозначным.

## D8. Отчёт — markdown как основной формат

**Решение.** `report.py` формирует markdown-таблицу по всем прогонам (инструмент × таймфрейм ×
тариф) и умеет сохранять сделки в CSV, сводку — в JSON.

**Почему.** Решение принимается человеком по диффу отчёта в git: markdown читается в PR и
позволяет сравнивать даты прогонов. Машинные форматы — вторичны.

## D9. Что модель издержек и PnL не учитывает

| Не учитывается | Следствие |
|---|---|
| Проскальзывание и очередь в стакане | Результат оптимистичен: реальные входы/выходы хуже на часть спреда |
| Абонентская плата тарифа (390 ₽/мес) | Фиксированные расходы не входят в «PnL после комиссии»; при малом обороте это заметная доля |
| Ступени ставок фьючерсов (0.03 %/0.025 % при обороте) | Расчёт идёт по базовой ставке 0.04 % — консервативно |
| Минимальная комиссия брокера | Параметр `min_commission_rub` есть, по умолчанию 0: тарифный документ нужно проверить при первом реальном прогоне |
| Внутрисделочная просадка | Max DD считается по реализованному PnL и занижен |

Эти допущения перечисляются в отчёте и `README.md`: цифры прогона — верхняя граница оценки,
а не обещание доходности.
