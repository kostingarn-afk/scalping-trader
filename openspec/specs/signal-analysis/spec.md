# Signal Analysis Specification

## Purpose

Анализ рыночных данных из Kafka, расчёт технических индикаторов, генерация торговых сигналов с предлагаемыми SL/TP и публикация в Kafka для исполнения.

## Requirements

### Requirement: Расчёт технических индикаторов

Analyzer SHALL рассчитывать на основе полученных свечей и стаканов индикаторы: RSI (period 7), MACD (8,21,5), Bollinger Bands (20,2), ATR (14), VWAP, order imbalance (из стакана depth=10).

#### Scenario: Получена серия свечей по инструменту
- **WHEN** Analyzer получает свечи по инструменту из конфигурации через Kafka `raw-market-data`
- **THEN** рассчитываются RSI, MACD, BB, ATR, VWAP; значения сохраняются в поле `indicators` (JSONB) записи `analysis_results`

#### Scenario: Получен стакан
- **WHEN** Analyzer получает стакан по инструменту из конфигурации
- **THEN** рассчитывается order imbalance (bid_vol - ask_vol)/(bid_vol + ask_vol) и сохраняется в `indicators.order_imbalance`

### Requirement: Генерация сигнала BUY/SELL/HOLD

Analyzer SHALL формировать сигнал на основе индикаторов с confidence (0.0–1.0), предлагаемой ценой входа, SL (от ATR) и TP, и временем устаревания (expires_at).

#### Scenario: Сигнал на покупку
- **WHEN** RSI < 30 и цена касается нижней BB (mean reversion)
- **THEN** генерируется сигнал BUY с confidence, suggested_price (лимитная), suggested_sl (entry - 1.5×ATR), suggested_tp (entry + 2×ATR), expires_at = now + 30с

#### Scenario: Нет сигнала
- **WHEN** индикаторы не дают уверенного сигнала
- **THEN** генерируется сигнал HOLD, в Kafka не публикуется (только сохраняется в БД)

### Requirement: Сохранение результатов анализа в БД

Analyzer SHALL сохранять каждый результат анализа в таблицу `analysis_results` с уникальным `signal_id` (UUID), `strategy_id`, `analyzer_version`.

#### Scenario: Сохранение результата
- **WHEN** Analyzer генерирует сигнал
- **THEN** в `analysis_results` вставляется запись с signal_id, ts, instrument_id, indicators, signal, confidence, suggested_price/sl/tp, expires_at

### Requirement: Публикация сигнала в Kafka

Analyzer SHALL публиковать сигналы BUY/SELL в Kafka-топик `trading-signals` в формате Protobuf (сообщение `TradingSignal`). HOLD не публикуется.

#### Scenario: Публикация BUY-сигнала
- **WHEN** сгенерирован сигнал BUY по инструменту из конфигурации
- **THEN** в Kafka `trading-signals` публикуется сообщение TradingSignal с signal_id, figi, signal=BUY, confidence, suggested_price/sl/tp, expires_at

### Requirement: Multi-process масштабирование

Analyzer SHALL работать как N процессов-консьюмеров в одной consumer group, с partitioning по `instrument_id` для распределения нагрузки. Число инструментов задаётся конфигурацией и не фиксируется требованием.

#### Scenario: Несколько инструментов
- **WHEN** в конфигурации N инструментов и 2 процесса-консьюмера
- **THEN** инструменты распределяются между процессами по partition key instrument_id, каждый процесс обрабатывает свои инструменты

### Requirement: Комиссионная фильтрация сигналов

Analyzer SHALL оценивать потенциальную валовую прибыль сигнала и отбрасывать сигналы, где прибыль менее 3× суммарной комиссии (вход + выход).

Ставка брокера за сторону MUST браться из конфигурации (`commission_rate_per_side`), а не из
константы в коде: «Инвестор» — 0.003, «Трейдер» — 0.0005. Смена тарифа меняет долю отсекаемых
сигналов (≈ 92 % на «Инвесторе» против единиц процентов на «Трейдере») и не требует правки кода.

#### Scenario: Сигнал не проходит комиссионный фильтр
- **WHEN** ожидаемая прибыль от сигнала < 3× комиссии, рассчитанной по ставке из конфигурации
- **THEN** сигнал отбрасывается (HOLD), в Kafka не публикуется, в БД сохраняется с пометкой причины отклонения

### Requirement: Потребление стакана и сделок

Analyzer SHALL разбирать из `raw-market-data` сообщения `ORDER_BOOK` и `TRADE` наравне со
свечами и хранить последнее состояние стакана и потока сделок по каждому инструменту.

Стакан SHALL попадать в расчёт индикаторов: `order_imbalance` в production-пути MUST
рассчитываться по переданным уровням, а не оставаться пустым. Сообщения без распознаваемого
payload MUST игнорироваться без остановки консьюмера.

#### Scenario: Стакан доходит до индикаторов

- **WHEN** по инструменту приходит сообщение `ORDER_BOOK`, затем завершённая свеча
- **THEN** в записи анализа для этой свечи `order_imbalance` рассчитан по объёмам bid и ask, а не пуст

#### Scenario: Стакан отсутствует

- **WHEN** по инструменту стакан ещё не приходил
- **THEN** `order_imbalance` остаётся пустым, а остальные индикаторы считаются как прежде

#### Scenario: Сделка без направления

- **WHEN** приходит сделка с направлением `UNSPECIFIED` и известна предыдущая цена сделки
- **THEN** направление определяется по тик-правилу: выше предыдущей — покупка, ниже — продажа, равна — предыдущее направление

#### Scenario: Битая полезная нагрузка

- **WHEN** сообщение не разбирается как `RawMarketData` или не содержит известного payload
- **THEN** оно пропускается, обработка следующих сообщений продолжается

### Requirement: VPIN по объёмным бакетам

Analyzer SHALL рассчитывать VPIN как среднее отношение `|объём покупок − объём продаж|` к
размеру бакета по последним завершённым бакетам фиксированного объёма.

Размер бакета и число бакетов MUST задаваться конфигурацией. Пока завершённых бакетов меньше
заданного числа, VPIN MUST быть пустым: частичное окно смещает оценку.

#### Scenario: Односторонний поток

- **WHEN** все сделки в окне направлены в одну сторону и набрано достаточно бакетов
- **THEN** VPIN близок к 1

#### Scenario: Сбалансированный поток

- **WHEN** объёмы покупок и продаж в каждом бакете равны
- **THEN** VPIN равен 0

#### Scenario: Данных недостаточно

- **WHEN** завершённых бакетов меньше заданного числа
- **THEN** VPIN пуст, и модель, требующая его, не входит в сделку

#### Scenario: Значение в записи анализа

- **WHEN** VPIN рассчитан к моменту завершённой свечи
- **THEN** он сохраняется в `analysis_results.indicators` вместе с остальными индикаторами
