## 1. Задача

Определить, есть ли у торговой системы положительное математическое ожидание **после издержек**.
Реальные деньги не вносятся до подтверждения.

**Критерий приёмки:** `gate` (`gross / комиссия`) ≥ 1, `t ≥ 2` на out-of-sample, ≥ 50 сделок,
прибыль переживает удаление 3 лучших периодов (считается автоматически, колонка
`Net без 3 лучших %`), устойчиво между инструментами и периодами.

| Параметр | Значение |
|---|---|
| Депозит (расчётный) | 200 000 ₽ |
| Риск на сделку / дневной лимит | 1 % / 3 % (`risk_config`) |
| Инструменты | параметр сессии; **отбор**: ATR(1h) ≥ 0.4 % (масштаб волатильности) и ATR(1min) ≥ 0.03 % (торговый фрейм), оборот ≥ 100 млн ₽/день |
| Торговый таймфрейм | **`1min`** (минимум API); `5min`/`15min` — только при доказанном преимуществе; `1h` и выше — анализ и отбор, не торговля |
| Цель выхода | `k × ATR(1min)`, где `k = ceil(0.30 / ATR(1min, %))`: порог 0.30 % задан `commission_profit_ratio × 2 × rate_per_side` (при `ratio = 3` и «Трейдере»); при ATR 0.03 % это `k = 10` |
| Тариф, на котором торговля возможна | «Трейдер» 0.05 % за сторону; в Analyzer-конфиге и `risk_config` должно стоять `commission_rate_per_side = 0.0005` — дефолт `0.003` («Инвестор») даёт порог 1.8 % и отсекает все минутные сигналы |
| Глубина истории | ≤ 1 год (глубже не выгружается) |
| Режим | sandbox |

## 2. Правила реализации (установлены замерами)

| Правило | Основание |
|---|---|
| **Торговый таймфрейм — `1min`; `1h` — только анализ** | API даёт минимум 1min (требование владельца). `5min`/`15min` — только при доказанном преимуществе. Часовой бар не является торговым горизонтом |
| **Вход только при EV > 0 после издержек** | `EV = p·avgWin − (1−p)·avgLoss − C − S`, где `avgWin/avgLoss` — до издержек, `C = 2 × rate_per_side` (0.10 % на «Трейдере»), `S` — спред. Живой фильтр `commission_filter` требует `abs(TP − entry) ≥ ratio × C` (`ratio = 3` → 0.30 %); ниже этого порога сигнал не публикуется |
| **5-дневный momentum при 10-дневном удержании не торгуется** | значимо убыточен: net −52 %, t −2.46; после удаления 3 лучших периодов −68 %, t −4.09 — убыток размазан по периодам, а не собран в трёх, поэтому это структура, а не везение |
| **Зеркальный разворот на тех же окнах не торгуется** | его прибыль (+47 %) держится на трёх моментах рынка: после обрезки +23 % при t 1.33, walk-forward OOS t 1.83 < 2 |
| Любой кандидат проходит проверку на концентрацию | если после удаления 3 лучших периодов знак меняется или t < 2 — преимущества нет |
| В панели издержки не ограничение (gate 20–27) | искать устойчивость сигнала, а не дешевизну |
| Запрет входов до 11:00 МСК | первый час основной сессии: −3.8 б.п. дрейфа, t −2.53 |
| Дневной стоп 3 % — правило портфеля | при 1 % риска на одну позицию не срабатывает (проверено) |
| Ротация бумаги: ≥ 15 % за окно **и** кандидат по фильтру | 15 % ≈ 1.8 сигмы шума; меньший порог срабатывает от случайности |
| История глубже 1 года не выгружается | требование владельца; глубина не создаёт преимущество |
| Состав списка — параметр сессии | отбор по ATR(1h)/ATR(1min) и обороту, а не по PnL бэктеста |

## 3. Состояние

**Закрыто и проверено** — повторно не открывать без новых данных:

- Mean reversion на одном имени: gross ≈ 0 на всех ТФ.
- Momentum на одном имени: 79 % net давали 3 сделки из 79.
- Панель: momentum (окна 5–63 дня), разворот, сигналы с поправкой на бету и риск — лучший OOS t 1.83.
- Пары и коинтеграция: Engle–Granger p ≥ 0.286 во всех 10 парах; Hurst в пределах шума.
- Внутридневная сезонность: ни один час не перекрывает круговую комиссию 10 б.п.

**Единственный устойчивый факт:** правило §2 о 5-дневном momentum (убыточен при 10-дневном удержании).

**Техническое состояние, важное для плана** (сверено с кодом 2026-11-21):

- В `analyzer/src/analyzer/backtest/cli.py:94` уже есть `--strategy {mean_reversion,momentum,v2}`; выбор реализован через `choices`, `_strategy_config` (`:506-531`) и `_builder_for` (`:552-556`), где неизвестный тип конфига молча уходит в `momentum`. Новая модель требует правки всех трёх мест: без последнего она будет считать чужой стратегией без ошибки.
- `strategy_v2.py` готов для бэктеста, но в live не переключён — образец «модель → бэктест → гейт → переключение».
- Ни одного `@RestController` в проекте нет: у UI отсутствует источник данных, кроме `/actuator/prometheus`.
- `positions` и `trade_results` заполняются при входе (`TradeOrchestrator:197` → `upsertPosition`; `insertTrade`, `updateRejectReason`), но закрытие в БД не пишется: `closePosition` и `updateTradeOnClose` объявлены и не вызываются; `orders` не заполняется.
- `RecoveryService.recover()` не вызывается, загрузки позиций на старте нет, `PnlCircuitBreaker` не подключён.
- Analyzer отбрасывает стакан, хотя Collector его публикует: модели микроструктуры требуют правки разбора сообщений.

### 4.1 Этап 1 — динамическая проработка сигналов (`analyzer`)

Основание — `docs/mat_analyze.md` (шесть подходов, критерий Келли, обобщённая формула EV,
план валидации). Точка расширения — существующий реестр `--strategy`. Все модели считаются
на **минутных** барах; часовой ряд — только контекст режима и отбор инструментов.

| Шаг | Работа | Критерий готовности |
|---|---|---|
| 1.1 | Единый протокол `SignalModel` (fit/predict/params) + конфиг; `mean_reversion`, `momentum`, `v2` переводятся без изменения поведения | golden-тесты: сигналы до и после совпадают на фиксированном ряду |
| 1.2 | OU mean reversion: θ/μ/σ в скользящем окне, вход по z-score остатка | на синтетике OU с известными параметрами оценки восстанавливаются в допуске |
| 1.3 | Микроструктура: VPIN и OBI. **Требует пропускать стакан** из `raw-market-data` (сейчас отбрасывается) | стакан доходит до модели; `order_imbalance` перестаёт быть `None` в production-пути |
| 1.4 | HMM-переключение режимов вместо ADX-эвристики как фильтр входа | на синтетике со сменой режима переключение обнаруживается до входа |
| 1.5 | Jump-diffusion / Hawkes: интенсивность кластеризации сделок | оценка интенсивности на синтетике Пуассона и Хоукса различается |
| 1.6 | Almgren–Chriss: модель издержек исполнения в бэктесте (проскальзывание, fill-цена) | сравнение с текущей моделью по `gate` и `t` |
| 1.7 | Келли как диагностика + настраиваемый потолок `kelly_cap_pct` (решение 4); Flyway V5 — новый ключ в `risk_config` | размер = `min(Келли, kelly_cap_pct, max_loss_per_trade_pct)`; потолок выше 1.0 действует только после поднятия `max_loss_per_trade_pct` |
| 1.8 | Автоматический гейт §1 в отчёте для каждого кандидата | отчёт печатает `gate`, `t` OOS, число сделок, `Net без 3 лучших %`; ADF, Ljung–Box, Jarque–Bera и split 70/30 входят в тот же прогон (`docs/mat_analyze.md` §5) |
| 1.9 | Порог покрытия издержек и множитель `k`: цель `k × ATR(1min)`, `k = ceil(0.30 / ATR(1min, %))` в рантайме; `config.py:26` → `commission_rate_per_side = 0.0005`; новая миграция `V8` (V5–V7 заняты) с `UPDATE risk_config` для той же ставки; правка `strategy.py` (сейчас `suggested_tp = entry + 2×ATR`) и спеки `signal-analysis` | сигнал ниже порога не публикуется; тест: цель `2×ATR` отбрасывается, цель ≥ порога проходит; в БД и конфиге 0.0005 (порог 0.30 %, `k ≈ 10`), а не 1.8 % |
| 1.10 | EV-оценка входа: `p`, `avgWin`, `avgLoss` по минутной истории с учётом всех исходов (TP, SL, таймаут), `S` — из стакана (после шага 1.3); сигнал публикуется только при `EV > 0` | тест: при `EV ≤ 0` сигнал не публикуется; таймаут и SL входят в `p`, а не только TP; параметры оценки — в конфиге |

`EV`-фильтр входа — отдельная величина: `expectancy_pct` в отчёте бэктеста (`avg_net / депозит`)
её не заменяет и в гейт входа не переносится.

Ограничения этапа:

- Production-путь Analyzer (`strategy.py`) не меняется до прохождения гейта; переключение — отдельный шаг.
- Шаг 1.6 не зависит от этапа 3: котирование LIMIT по Avellaneda–Stoikov вынесено в 3.6, потому что это исполнение, а не сигнал.
- Параметры моделей — в конфиге, не в коде; оценка — только на train-части, с purge/embargo из `docs/monitoring.md` §3.
- Новые зависимости — только по разрешению владельца (HMM требует `hmmlearn`; вопрос 5.3).
- Низкочастотные модели не подменяют скальпинговую логику: горизонт удержания остаётся в пределах `max_holding_time_minutes`.

### 4.2 Этап 2 — мониторинг моделей (`analyzer`)

Основание — `docs/monitoring.md`. Система **поднимает сигнал**, решение принимает пользователь:
автопереобучения, автозамены модели и автоматического изменения `risk_config` нет.

| Шаг | Работа | Критерий готовности |
|---|---|---|
| 2.1 | Flyway V6 (V5 занят `kelly_cap_pct` из 1.7): таблица `monitor_events` (`ts`, `model`, `instrument`, `level`, `metric`, `observed`, `threshold`, `recommendation`, `status`, `cooldown_until`, `decided_by`, `decided_at`) | миграция применяется на чистой БД |
| 2.2 | Четыре уровня триггеров: структурные сдвиги, дрейф параметров с uncertainty, деградация предсказательной силы (DSR, alpha decay, Brier Score), мета-мониторинг | каждый уровень воспроизводится на синтетике |
| 2.3 | Поправка на множественное тестирование: α = 0.05, Бонферрони для уровня 1, FDR (Бенджамини–Хохберг) для уровней 3–4, bootstrap-пороги для метрик без p-value | на нулевых сериях доля ложных срабатываний не выше α |
| 2.4 | Публикация события: запись в БД + лог + метрика `monitor_events_total{level,model}` | событие видно до появления UI |
| 2.5 | Решение человека: approve создаёт задачу на прогон, reject — с причиной и cooldown | ни одного автозапуска переобучения в коде |

Предусловие: накопленная история (раздел 5.1). Без свежих данных триггеры считают шум.

Shadow trading и statistical equivalence (`docs/monitoring.md` §6) в объём не входят: они требуют
промышленного потока сделок и включаются после выхода в live, а не на бэктест-контуре.

### 4.3 Этап 3 — UI

**Стек (решение 1):** React + TypeScript (Vite) + FastAPI.

- `ui/web` — React + TypeScript; свечи — `lightweight-charts`, отчётные графики — Recharts/Plotly.
- `ui/api` — FastAPI: читает PostgreSQL (read-model) и проксирует действия в Trader REST.

**Источник данных (решение 2):** действия и текущее состояние — REST в Trader; история и агрегаты —
read-model из БД. UI не пишет в БД напрямую и не знает токена T-Invest.

| Шаг | Работа | Критерий готовности |
|---|---|---|
| 3.0 | REST в Trader: `/api/trading/state`, `/api/positions`, `/api/orders`, `/api/risk`, `/api/trading/start`, `/api/trading/stop` | первый `@RestController`; ответы без секретов; health-тест |
| 3.1 | Журнал и восстановление: закрытие позиций в БД (`closePosition`, `updateTradeOnClose` — сейчас не вызываются), заполнение `orders`, `RecoveryService.recover()` при старте со сверкой с БД (сейчас опущена — `RecoveryService:41`) | после рестарта состояние совпадает с биржей; закрытые сделки отражены в `trade_results` и `positions` |
| 3.2 | Дашборд торгов: вход и текущая цена, стоп-точка (SL), end-точка (TP), PnL и комиссия по сделке, дневной лимит, статус | PnL и комиссия считаются в Trader (сейчас не считаются); снимок UI совпадает с `trade_results` и `positions` |
| 3.3 | Start/Stop: `LiquidationWorker` — отдельный процесс ликвидации (решение 3) + Flyway V7 — таблица состояния (`RUNNING`/`HALTING`/`FAILED`/`STOPPED`) | тест на sandbox: все позиции закрыты, Trader остановлен только после завершения ликвидатора |
| 3.4 | Дашборд моделей и мониторинга: параметры, метрики деградации, pending-события, approve/reject | approve создаёт задачу, но не запускает переобучение |
| 3.5 | Отчёт по выгруженным данным: период/тикеры/интервал, агрегация, графики с подписями, экспорт в Markdown и PNG/PDF | строится офлайн из `data/history-1min`, без сети; переиспользует `backtest/{loader,engine,report}.py` |
| 3.6 | Котирование LIMIT по Avellaneda–Stoikov (опция): цена входной заявки по модели | сравнение с текущей ценой по доле исполнения и издержкам; выключено по умолчанию |

**Механика stop (решение 3):**

1. Запускается отдельный процесс `LiquidationWorker`; Trader переходит в `HALTING`: новые сигналы отбрасываются с метрикой, состояние пишется в БД и переживает рестарт.
2. Снятие активных стоп-заявок — иначе возможно двойное закрытие.
3. Закрытие LIMIT по лучшей цене на момент старта; допуск и таймаут — в `risk_config`, не в коде.
4. По таймауту — эскалация в MARKET через `emergencyClose` (переиспользуется, но обёртывается ожиданием подтверждения; сейчас `AutoCloseService` его не ждёт).
5. Опрос `GetOrderState` до подтверждённого закрытия каждой позиции.
6. Ликвидатор завершается **только** когда все позиции закрыты; Trader останавливается после его успешного завершения. При недоступности API — статус `FAILED` и алерт, а не «успех».
7. Повторный stop идемпотентен: незавершённая ликвидация продолжается, а не дублируется.
8. Ручной stop — тоже emergency-сценарий: в рамках 3.3 обновляются `AGENTS.md` §7 и javadoc `OrderExecutionService`, где MARKET разрешён только для PnL-CB.

**Ограничения этапа:** UI торговли — только sandbox до подтверждения §1; start/stop доступны только
с localhost или по токену UI (вопрос 5.3); в UI и API нет токенов T-Invest.

### 5.2 Принятые решения (2026-11-21)

| № | Вопрос | Решение |
|---|---|---|
| 1 | Стек UI | **React + TypeScript + FastAPI**; фронтенд и API — отдельные каталоги `ui/web`, `ui/api` |

| 3 | Механика stop | **LIMIT по лучшей цене → таймаут → эскалация в MARKET** (`emergencyClose`); завершение только после подтверждённого закрытия всех позиций |
| 4 | Келли и потолок риска | Келли — диагностика и ограничитель размера; потолок настраиваемый с плавающей точкой: `kelly_cap_pct numeric(4,2)`, диапазон 0.1–5.0, шаг 0.1 (0.5, 1.0, 1.1, 2.5, 3.0 и т. д.); фактический риск = `min(Келли, kelly_cap_pct, max_loss_per_trade_pct)`. Потолок выше 1.0 действует только после поднятия `max_loss_per_trade_pct` — иначе `min` возвращает 1.0 |

## 7. Что не делать

| Антипаттерн | Почему |
|---|---|
| Менять бумагу по результату бэктеста | подгонка под шум: на новых данных убыточной окажется другая |
| Менять бумагу при убытке меньше 15 % | шум бумаги за 20 торговых дней ≈ 8.5 % |
| Оценивать результат без обрезки лучших периодов | 2–3 периода дают половину «прибыли» |
| Сравнивать дрейф часа с нулём, а не с издержками | круговая комиссия 10 б.п. больше любого часового дрейфа |
| Выгружать историю глубже 1 года | запрещено требованием |
| Вносить деньги до подтверждённого edge | проверка гипотезы стоит времени, а не денег |
| Запускать переобучение автоматически по сигналу мониторинга | сигнал — рекомендация; решение и ответственность за человеком |
| Включать модель в live без прохождения гейта §1 | бэктест-контур и торги — разные режимы ответственности |
| Давать UI прямой доступ к токену T-Invest | один канал к брокеру, токен не покидает Trader |
| Открывать start/stop в публичную сеть | это прямые торговые действия, не дашборд |
