## 1. Задача

Определить, есть ли у торговой системы положительное математическое ожидание **после издержек**.
Реальные деньги не вносятся до подтверждения.

**Критерий приёмки:** `gate` (`gross / комиссия`) ≥ 1, `t ≥ 2` на out-of-sample, ≥ 50 сделок,
прибыль переживает удаление 3 лучших периодов, устойчиво между инструментами и периодами.
Проверка считается автоматически в каждом прогоне бэктеста (раздел «Гейт §1» отчёта).

| Параметр | Значение |
|---|---|
| Депозит (расчётный) | 200 000 ₽ |
| Риск на сделку / дневной лимит | 1 % / 3 % (`risk_config`) |
| Инструменты | параметр сессии; **отбор**: ATR(1h) ≥ 0.4 % (масштаб волатильности) и ATR(1min) ≥ 0.03 % (торговый фрейм), оборот ≥ 100 млн ₽/день |
| Торговый таймфрейм | **`1min`** (минимум API); `5min`/`15min` — только при доказанном преимуществе; `1h` и выше — анализ и отбор, не торговля |
| Цель выхода | `k × ATR(1min)`, где `k = ceil(порог / ATR(1min, %))`; порог = `2·ratio·rate/(1 − ratio·rate)·100` (круг по обеим ногам) ≈ 0.30 % при `ratio = 3` и «Трейдере» |
| Тариф | «Трейдер» 0.05 % за сторону: `commission_rate_per_side = 0.0005` в конфиге Analyzer и в `risk_config` (миграция `V6`) |
| Глубина истории | ≤ 1 год (глубже не выгружается) |
| Режим | sandbox |

## 2. Правила реализации (установлены замерами)

| Правило | Основание |
|---|---|
| **Торговый таймфрейм — `1min`; `1h` — только анализ** | API даёт минимум 1min (требование владельца). `5min`/`15min` — только при доказанном преимуществе. Часовой бар не является торговым горизонтом |
| **Вход только при EV > 0 после издержек** | `EV = p·avgWin − (1−p)·avgLoss − C − S`; в коде комиссия и издержки исполнения уже внутри `net_pnl`, поэтому вычитаются один раз. Гейт исполняют бэктест (по сделкам прогона) и Trader (по `trade_results`) |
| **5-дневный momentum при 10-дневном удержании не торгуется** | значимо убыточен: net −52 %, t −2.46; после удаления 3 лучших периодов −68 %, t −4.09 — убыток размазан по периодам, а не собран в трёх, поэтому это структура, а не везение |
| **Зеркальный разворот на тех же окнах не торгуется** | его прибыль (+47 %) держится на трёх моментах рынка: после обрезки +23 % при t 1.33, walk-forward OOS t 1.83 < 2 |
| Любой кандидат проходит проверку на концентрацию | если после удаления 3 лучших периодов знак меняется или t < 2 — преимущества нет |
| В панели издержки не ограничение (gate 20–27) | искать устойчивость сигнала, а не дешевизну |
| Запрет входов до 11:00 МСК | первый час основной сессии: −3.8 б.п. дрейфа, t −2.53 |
| Дневной стоп 3 % — правило портфеля | при 1 % риска на одну позицию не срабатывает (проверено) |
| Ротация бумаги: ≥ 15 % за окно **и** кандидат по фильтру | 15 % ≈ 1.8 сигмы шума; меньший порог срабатывает от случайности |
| История глубже 1 года не выгружается | требование владельца; глубина не создаёт преимущество |
| Состав списка — параметр сессии | отбор по ATR(1h)/ATR(1min) и обороту, а не по PnL бэктеста |

## 3. Состояние

**Закрыто и проверено** — повторно не открывать без новых данных:

- Mean reversion на одном имени: gross ≈ 0 на всех ТФ.
- Momentum на одном имени: 79 % net давали 3 сделки из 79.
- Панель: momentum (окна 5–63 дня), разворот, сигналы с поправкой на бету и риск — лучший OOS t 1.83.
- Пары и коинтеграция: Engle–Granger p ≥ 0.286 во всех 10 парах; Hurst в пределах шума.
- Внутридневная сезонность: ни один час не перекрывает круговую комиссию 10 б.п.

**Единственный устойчивый факт:** правило §2 о 5-дневном momentum (убыточен при 10-дневном удержании).

**Итог этапа 1** (шаги 1.1–1.10, архив `openspec/changes/archive/2026-11-22-*`):

- Инфраструктура готова: протокол моделей `SignalModel` + реестр (OU, HMM, Hawkes, микроструктура,
  momentum, v2), издержки исполнения Almgren–Chriss, цель `k×ATR` от порога комиссии, гейт §1
  и диагностика ряда в отчёте, EV-гейт входа, Келли-потолок в Trader.
- **Гейт §1 не пройден ни одной моделью.** Прогон AFLT 1min (280 958 баров, `trader`, спред 5 +
  импакт 10 б.п.): mean reversion с целью `k×ATR` — 50 сделок, net −13 % депозита, `t` OOS −39;
  без EV-гейта — 9 258 сделок и −2 595 % депозита. Вывод: на минутном горизонте с этими
  издержками у правила нет преимущества, и EV-гейт это фиксирует, останавливая торговлю.
- Источник истины по поведению моделей — `analyzer/README.md` §5, §11; по риск-контуру —
  `trader/README.md`.

**Техническое состояние, важное для плана** (сверено с кодом 2026-11-22):

- `strategy_v2.py` готов для бэктеста, но в live не переключён — образец «модель → бэктест → гейт → переключение».
- Ни одного `@RestController` в проекте нет: у UI отсутствует источник данных, кроме `/actuator/prometheus`.
- `positions` и `trade_results` заполняются при входе (`TradeOrchestrator:197` → `upsertPosition`; `insertTrade`, `updateRejectReason`), но закрытие в БД не пишется: `closePosition` и `updateTradeOnClose` объявлены и не вызываются; `orders` не заполняется. Пока это так, оценки Келли и EV в Trader не пополняются и оба гейта не действуют.
- `RecoveryService.recover()` не вызывается, загрузки позиций на старте нет, `PnlCircuitBreaker` не подключён.

## 4. План шагов

### 4.0 Приоритет и зависимости

| Этап | Цель | Зависит от | Гейт §1 |
|---|---|---|---|
| **1. Анализ сигналов** | расширить набор моделей `analyzer` по `docs/mat_analyze.md`, каждую — через бэктест и гейт | — | **закрыт**: модели есть, гейт не пройден |
| **2. Мониторинг** | сигнал о деградации модели; решение о переобучении принимает человек (`docs/monitoring.md`) | модель, прошедшая гейт §1 | нет (мониторинг не торгует) |
| **3. UI** | наблюдение за моделями, мониторингом и торгами; start/stop; отчёт по выгруженным данным | 2.1–2.4 — иначе дашборд пуст | для live |

Правила порядка:

- Этап 2 нельзя начинать раньше, чем модель из этапа 1 проходит гейт: мониторить нечего.
- Подэтап 3.0 (REST в Trader) можно делать параллельно с этапом 2 — он не зависит от моделей.
- **Ни одна модель и ни один live-режим не включается до прохождения §1.** UI торговли — только sandbox.
- Каждый подэтап завершается тестами и отчётом; «сделано» без проверки не отмечается.

### 4.2 Этап 2 — мониторинг моделей (`analyzer`)

Основание — `docs/monitoring.md`. Система **поднимает сигнал**, решение принимает пользователь:
автопереобучения, автозамены модели и автоматического изменения `risk_config` нет.

| Шаг | Работа | Критерий готовности |
|---|---|---|
| 2.1 | Flyway `V8` (`V5` — `kelly_cap_pct`, `V6` — ставка, `V7` — `ev_min_trades`): таблица `monitor_events` (`ts`, `model`, `instrument`, `level`, `metric`, `observed`, `threshold`, `recommendation`, `status`, `cooldown_until`, `decided_by`, `decided_at`) | миграция применяется на чистой БД |
| 2.2 | Четыре уровня триггеров: структурные сдвиги, дрейф параметров с uncertainty, деградация предсказательной силы (DSR, alpha decay, Brier Score), мета-мониторинг | каждый уровень воспроизводится на синтетике |
| 2.3 | Поправка на множественное тестирование: α = 0.05, Бонферрони для уровня 1, FDR (Бенджамини–Хохберг) для уровней 3–4, bootstrap-пороги для метрик без p-value | на нулевых сериях доля ложных срабатываний не выше α |
| 2.4 | Публикация события: запись в БД + лог + метрика `monitor_events_total{level,model}` | событие видно до появления UI |
| 2.5 | Решение человека: approve создаёт задачу на прогон, reject — с причиной и cooldown | ни одного автозапуска переобучения в коде |

Предусловие: накопленная история (раздел 5.1). Без свежих данных триггеры считают шум.

Shadow trading и statistical equivalence (`docs/monitoring.md` §6) в объём не входят: они требуют
промышленного потока сделок и включаются после выхода в live, а не на бэктест-контуре.

### 4.3 Этап 3 — UI

**Стек (решение 1):** React + TypeScript (Vite) + FastAPI.

- `ui/web` — React + TypeScript; свечи — `lightweight-charts`, отчётные графики — Recharts/Plotly.
- `ui/api` — FastAPI: читает PostgreSQL (read-model) и проксирует действия в Trader REST.

**Источник данных (решение 2):** действия и текущее состояние — REST в Trader; история и агрегаты —
read-model из БД. UI не пишет в БД напрямую и не знает токена T-Invest.

| Шаг | Работа | Критерий готовности |
|---|---|---|
| 3.0 | REST в Trader: `/api/trading/state`, `/api/positions`, `/api/orders`, `/api/risk`, `/api/trading/start`, `/api/trading/stop` | первый `@RestController`; ответы без секретов; health-тест |
| 3.1 | Журнал и восстановление: закрытие позиций в БД (`closePosition`, `updateTradeOnClose` — сейчас не вызываются), заполнение `orders`, `RecoveryService.recover()` при старте со сверкой с БД (сейчас опущена — `RecoveryService:41`), `candle_interval` из фактического интервала вместо константы `"1min"` (`main.py:71`) | после рестарта состояние совпадает с биржей; закрытые сделки отражены в `trade_results` и `positions`; оценки Келли и EV в Trader пополняются |
| 3.2 | Дашборд торгов: вход и текущая цена, стоп-точка (SL), end-точка (TP), PnL и комиссия по сделке, дневной лимит, статус | PnL и комиссия считаются в Trader (сейчас не считаются); снимок UI совпадает с `trade_results` и `positions` |
| 3.3 | Start/Stop: `LiquidationWorker` — отдельный процесс ликвидации (решение 3) + Flyway `V9` — таблица состояния (`RUNNING`/`HALTING`/`FAILED`/`STOPPED`) | тест на sandbox: все позиции закрыты, Trader остановлен только после завершения ликвидатора |
| 3.4 | Дашборд моделей и мониторинга: параметры, метрики деградации, pending-события, approve/reject | approve создаёт задачу, но не запускает переобучение |
| 3.5 | Отчёт по выгруженным данным: период/тикеры/интервал, агрегация, графики с подписями, экспорт в Markdown и PNG/PDF | строится офлайн из `data/history-1min`, без сети; переиспользует `backtest/{loader,engine,report}.py` |
| 3.6 | Котирование LIMIT по Avellaneda–Stoikov (опция): цена входной заявки по модели | сравнение с текущей ценой по доле исполнения и издержкам; выключено по умолчанию |

**Механика stop (решение 3):**

1. Запускается отдельный процесс `LiquidationWorker`; Trader переходит в `HALTING`: новые сигналы отбрасываются с метрикой, состояние пишется в БД и переживает рестарт.
2. Снятие активных стоп-заявок — иначе возможно двойное закрытие.
3. Закрытие LIMIT по лучшей цене на момент старта; допуск и таймаут — в `risk_config`, не в коде.
4. По таймауту — эскалация в MARKET через `emergencyClose` (переиспользуется, но обёртывается ожиданием подтверждения; сейчас `AutoCloseService` его не ждёт).
5. Опрос `GetOrderState` до подтверждённого закрытия каждой позиции.
6. Ликвидатор завершается **только** когда все позиции закрыты; Trader останавливается после его успешного завершения. При недоступности API — статус `FAILED` и алерт, а не «успех».
7. Повторный stop идемпотентен: незавершённая ликвидация продолжается, а не дублируется.
8. Ручной stop — тоже emergency-сценарий: в рамках 3.3 обновляются `AGENTS.md` §7 и javadoc `OrderExecutionService`, где MARKET разрешён только для PnL-CB.

**Ограничения этапа:** UI торговли — только sandbox до подтверждения §1; start/stop доступны только
с localhost или по токену UI (вопрос 5.3); в UI и API нет токенов T-Invest.
